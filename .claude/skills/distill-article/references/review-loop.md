# 審查迴圈

卡寫完、`validate_card.py` PASS 之後，依序過三關。**一關一關來，不同時改**：卡同時被兩種審查者要求修改很難收斂（第一次實跑的教訓）。

```
對證者迴圈（最多 5 輪）→ 讀者迴圈（最多 5 輪）→ 全文審查（每篇文章一次）
   只看引文                   只看卡本身              讀整篇 blog，審這篇的所有卡
```

為什麼這樣排：對證者只需要「卡加引用的原文」，不用讀整篇 blog，輸入量小；先讓對證者把每條主張對到原文，卡穩定後才給讀者，讀者的結果不會因為對證者改卡而作廢（第一次實跑讀者與對證者同時跑，約 147 萬讀者 token 多半被後續改卡作廢）；整篇 blog 只在最後讀一次。

## 共通機制

| 機制 | 做法 |
|---|---|
| 每輪全新審查者 | 每輪都用全新 subagent，看不到撰寫者推理、其他卡、上一輪結果 |
| 引用由程式驗證 | 審查者引用的原文必須逐字出現在 blog（對證者還要出自給它的卡副本）；捏造的引用視為審查者的錯，改列備註、不擋卡 |
| 只指出問題 | 退回清單每條含：卡上哪一句、違反哪種錯誤、原文對應。審查者不得替撰寫者寫句子 |
| 撰寫者不能反駁 | 認為審查錯了，只能把該條標「爭議」交給人，立刻交，不等輪數用完 |
| 補卡 | 審查者發現卡漏掉東西時，由撰寫者自己補（只能來自 blog）；補進去或改動的主張要再過對證者 |
| 改動即失效 | 後面關卡看到的卡必須是「前面關卡通過的版本」。任何一關要求改卡 → `claim_fingerprints.py diff` 找出改過的主張 → 這些主張回到對證者重審 → 再重跑讀者 |
| pending 主張不擋 | `pending_author_confirmation` 的主張必然含 blog 矛盾，它的問題只記錄，不計入通過條件 |
| 輪數上限 | 用完仍有 blocker：停止，升級給人，附未解決的問題，**不自動放行** |

## 分級退回（blocker 與 minor）

第一次實跑一開始「任何一個原子不是完全支持就整張退回」，第 2、3 輪多為低價值的措辭退回。改成：

| 等級 | 內容 | 結果 |
|---|---|---|
| **blocker** | 判定「不支持」「找不到」；固定錯誤：數字對不上、範圍被放大、因果說得比原文強、夾帶 blog 沒有的判斷、限定條件掉了、舉例變成唯一；卡標「官方宣稱」卻其實不是（錨點類型標錯） | 整張卡退回 |
| **minor** | 主張與來源措辭不同、來源引用沒涵蓋但 blog 有支持、限定詞沒定義、相鄰錨點邊界爭議、主張互核矛盾（常是 blog 自己的）、審查者自己的引用錯誤、部分支持而無上列錯誤 | 只記錄在備註；撰寫者可順手修，不必修 |

「預設不通過、引用必須逐字」的舉證責任不變，變的只是「什麼會擋下整張卡」。第一次實跑以此重算第 3 輪：11 張中 7 張無 blocker。

## 關卡 1：對證者迴圈（`auditor_max_rounds`，預設 5）

1. 產生對證者版卡：
   `make_auditor_copy.py <card.md> <scratch>/<card>-aud.md`
   主張後標 `[n]`，卡尾是參考文獻（blog 逐字原文）與引文所在的 blog 段落。`stage1.auditor_context: quote` 可改成只給引文（最省，但看不到前後句；斷章取義改由全文審查抓）。
2. 派全新 subagent，用 `auditor-prompt.md`，變數：`AUDITOR_COPY`、`OUT_PATH`、`ONLY_CLAIMS`（第 1 輪省略）。
3. `verify_audit.py <card.md> <out.json> --copy <aud.md> [--only ids]`。有 blocker → 撰寫者修 → `validate_card.py` → 下一輪。
4. 第 2 輪起只審「新增或改過的主張」：
   - 通過的主張指紋存起來：`claim_fingerprints.py save <accepted.json> <card.md> [--blockers c1,c2]`
   - 下一輪：`claim_fingerprints.py diff <accepted.json> <card.md>` → 得到 id 清單 → `make_auditor_copy.py ... --only <ids>` → 提示詞的 `ONLY_CLAIMS` 填同一份清單 → `verify_audit.py ... --only <ids>`
5. 沒有 blocker → 過關。

對證者**看不到整篇 blog**，所以「blog 其他段落的矛盾」「卡漏掉的重點」「跨卡矛盾」它抓不到，這些由關卡 3 負責。

## 關卡 2：讀者迴圈（`reader_max_rounds`，預設 5）

讀者的設定：**懂一般 AI 工程詞彙、但沒讀過這篇 blog 的工程師。**

1. `make_reader_copy.py <card.md> <scratch>/<card>-reader.md`：移除引用與參考文獻（`source_quotes`、`qualifiers[].source_quote`、sources 區）。讀者看到的就是讀者會讀到的卡。
2. 撰寫者為每張卡出題：3 題確定在卡上有答案的專屬題（例如這個數字的比較對象是誰、限定條件是什麼、方法是誰提出的），加 1～2 題**陷阱題**（卡上確定沒有答案；從 blog 取一個卡沒收的事實）。陷阱題放最後，題號用 `--trap` 指定。
3. 派全新 subagent，用 `reader-prompt.md`。
4. `verify_reader.py <reader-copy.md> <reader.json> --trap <題號...>`：
   - 主軸三題（論點、機制、證據）每題都要有「卡上真的存在」的引用；引用不出來就算需要外部知識，退回。
   - 專屬題：有答案卻答「卡上沒寫」→ 漏看，退回；硬答沒有有效引用 → 退回。
   - 陷阱題：硬答 → 退回；答「卡上沒寫」→ 通過。
   - 名詞：標「擋住主軸理解」才退回；其餘只是建議。
5. 退回 → 撰寫者修卡（常是補脈絡主張或定義自創詞）→ `validate_card.py` → **改動的主張補審對證者**（`claim_fingerprints.py diff` → 關卡 1 的 `--only` 流程，這段補審另計，上限 `reader_edit_reaudit_max_rounds`，預設 2，超過交給人）→ 再跑讀者（算讀者輪數）。

為什麼題目由撰寫者出：通用題（比較對象、限定條件）在沒有該項的卡上，「沒寫」是正確答案，程式不知道哪題真的沒有。已知缺點：題目由撰寫者出會削弱獨立性，見 `docs/backlog.md`。

## 關卡 3：全文審查（`final_audit_max_rounds`，預設 2）

一篇文章只做一次，在這篇所有卡的關卡 1、2 都通過之後。**一個**審查者讀整篇 blog，同時審這篇文章提煉出的所有卡，全文只讀一次。

1. 派全新 subagent，用 `final-audit-prompt.md`，變數：`BLOG_PATH`、`CARD_PATHS`、`OUT_PATH`。
2. `verify_final_audit.py <final.json> <card.md>...`：
   - blocker：斷章取義；限定條件掉了；錨點歸屬錯（卡標官方宣稱時）。
   - 交人裁決（exit 2）：跨卡矛盾、blog 內部矛盾。預設處理：不修 blog，有矛盾的主張標 pending 或改保守寫法，由人確認。
   - 只記錄：卡漏掉重點、其他錨點邊界、pending 主張的問題。
3. 有 blocker → 撰寫者修 → 改動的主張補審對證者 → 再跑讀者（改動涉及主張內容時）→ 再跑一次全文審查（第 2 輪，之後仍有 blocker 就交人）。

## 執行細節

- subagent 並行上限 20；分批派發，派完用檔案數核對應到／實到。
- 審查產出放暫存目錄：`<scratch>/review/<card>/round<N>-auditor.json` 之類，不進 repo。
- 讀者、對證者、全文審查者各自的輸出 JSON 格式見各提示詞。
- 派發訊息只給提示詞路徑與變數；提示詞裡寫「只准讀這個檔案」指的是資料檔，提示詞檔本身當然要讀。

## 成本參考（第一次實跑，舊流程）

對證者每個約 8～9 萬 token（要讀整篇約 3 萬字的 blog），讀者約 4 萬；11 張卡三輪全面重審共 64 個 subagent、約 460 萬 token。新流程的預期：對證者輸入從整篇 blog（約 2 萬字）降到卡副本（paragraph 模式 3 千～1.6 萬字，quote 模式 0.7 萬字上下；補審 `--only` 約 3 千字）；讀者只審穩定的卡；全文審查每篇一次。實際用量要在下一次實跑時量，結果記進 `docs/`。
